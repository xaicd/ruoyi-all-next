# Online low-code engine

Phase 2 adds tenant-scoped PostgreSQL metadata persistence for Definition, Revision, Field, Index, Relation, View, Action, Policy, WorkflowBinding, Release, SchemaChange, and TestSession records. It intentionally has no in-memory fallback: Online metadata routes fail closed when PostgreSQL is unavailable.

The protected management lifecycle is now available: create a Definition with its initial Draft Revision, edit Definition/Draft metadata using `expectedLockVersion`, validate the Draft, create a semantic Schema Plan, publish an immutable SHA-256-protected Release snapshot, and atomically point the Definition back to a prior Release. Published revisions are immutable; publication creates a separate next Draft Revision.

Phase 3 accepts only structured Model IR and generates deterministic field/index operations with a fingerprint and risk level. A plan never accepts, stores, or exposes executable SQL. Changing a Draft model supersedes its open plans; low-risk plans can be approved with an audited note, while destructive and unsupported plans cannot be approved. For PostgreSQL `SINGLE + MANAGED_TABLE` definitions, an explicitly confirmed apply operation executes only server-derived, approved DDL: initial table creation, additive nullable columns, and ordinary indexes. A release is blocked until its current managed-table plan has been applied successfully.

Phase 4 adds a protected browser-based Online Test (功能测试) for published Definitions. Starting a test resolves the current Published Release, verifies its checksum, creates an actor-owned sandbox session, and validates CRUD values solely against that immutable Release model. The AUTO page at `/admin/infra/online-runtime/[definitionCode]` follows Jeecg: query, toolbar, list, create/edit dialog, and detail. `SINGLE` uses the default list; `TREE` uses a tree list with add-child and cycle-safe delete; `MASTER_DETAIL` uses ERP / INNER / TAB layouts. Each record is tenant-, definition-, release-, and test-session-scoped; Draft revisions and production business tables are never read or written by this path. Import/export, policy, and workflow remain disabled.

Phase 5 adds safe Puck presentation views. Drafts may store only registered Online components and controlled Definition/view/field/action bindings in `online_view`; the server validates size, depth, component keys, props, prototype keys, and Draft field/action references. Saving a Draft invalidates validation, validation fingerprints the normalized views, and publish checksums the normalized views inside the immutable Release snapshot before cloning them to the next Draft. Online Test renders a preview only from that compiled Release snapshot and uses the same component config as the editor. No view metadata may contain an endpoint URL, HTML, JavaScript, SQL, event handler, or executable behavior.

Puck rendering is presentation-only. Online 功能测试 remains sandbox-only (`online_record`, actor-owned session). Production ZIP CRUD is available only for a published `SINGLE + MANAGED_TABLE` Release whose managed-table schema revision and model fingerprint match its registry. The generated service is a thin tenant-scoped facade over `KyselyOnlineManagedTableRuntimeRepository`: it resolves only the current immutable Release, accepts only model allow-listed fields, applies Release action configuration, parameterizes all values, and adds `tenant_id` plus `deleted = false` to every read and mutation. The generated route receives the authenticated tenant/user context; it never accepts a table name, tenant ID, release ID, or schema revision from the client. Workflow execution, report/chart/dashboard queries, and Generic Record production ZIP CRUD remain disabled until their separate policy, audit, and transaction boundaries are implemented. The `online_record` migration is intentionally present but not deployed by this module; deploy it only through an approved staging/production migration runbook.
