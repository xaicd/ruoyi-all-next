# 需求：电商平台

状态：`PLAN_APPROVED`　特性：`ecommerce`　域名：`shop`

## 1. 目标

在基座上交付一个可运营的电商最小闭环：商品、库存、下单、支付。范围刻意收在「能跑通一笔交易」。

## 2. 角色

| 角色 | 能力 |
|---|---|
| 平台运营（admin） | 商品上下架、看订单、处理异常单 |
| 商家（admin，租户内） | 维护自己的商品与库存 |
| C 端用户（member） | 浏览、下单、支付、查看订单 |

## 3. 用户故事（按优先级）

1. **P0** 运营可以创建/编辑/上架/下架商品，带名称、价格、状态。
2. **P0** 库存不能被超卖：并发下单时可用量不足必须拒绝，且数据不被改动。
3. **P0** 用户可以下单：生成订单、预占库存；取消则释放预占。
4. **P0** 订单状态机 待支付→已支付→（仅退款可）已关闭；重复支付回调不得重复发业务事件。
5. **P1** 运营可在后台看到订单列表并筛选状态。
6. **P2** C 端可在 expo 端浏览商品列表。

## 4. 约束

* 多租户：所有业务表带 tenant_id，从全局上下文取，禁止调用方透传（AGENTS §4.8）。
* 跨域：库存与支付走 Facade（wms 的 lockStock/releaseStock、pay 的回调状态机），不得直接 import 别的域 Service（§3.3）。
* 不新增原生域：shop 是定制业务，落在本工程内，不回写基座（§17.3）。
* 全动词：GET/POST/PUT/DELETE 齐全，禁止只读骨架（§5.1）。
* 可被 agent 驱动：UI 带 Agent-Native 属性；每张表随代码产出 Agent 契约（§5.2.1）。

## 5. 验收标准

1. `npm run check` exit=0；`vitest` 内存模式全绿。
2. 全新库 `prisma migrate deploy` exit=0，`shop_product` 建表成功。
3. 侧边栏能看到 shop 域菜单（RBAC + 租户套餐两条链都通）。
4. 并发扣减只有一个成功，且失败方不改变数据（真实库用例）。
5. 支付回调重复到达不再发业务事件（幂等）。
6. storefront（C 端）能看到商品列表（Agent 契约驱动的 schema）。

## 6. 不做什么

* 不做营销/优惠券/会员等级（后续迭代）
* 不做真实支付渠道对接（先复用 pay 的状态机与回调契约）
* 不做库存调拨/盘点（复用 wms 既有能力）
