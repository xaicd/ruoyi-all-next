# DAR-20261009: 跨域服务间通信总线协议选型与事务边界决策

- **决策标识**: `DAR-20261009-MESSAGE-BUS-PROTOCOL`
- **决策主题**: 跨域与服务间消息总线协议选型与可靠投递事务边界
- **决策负责人**: @architect-team
- **评估日期**: 2026-10-09
- **归属规范**: CMMI 01_management (PLAN/MC/DAR) / `.agents/skills/dar-decision-matrix`
- **关联 ADR**: `ADR-0018: 采用自研 NATS 语义实现跨域可靠消息总线`

---

## 1. 决策目标与背景阐述 (Context & Problem Statement)

随着 `ruoyi-all-next` 从单体架构向模块化插件（15 个第一方业务插件 + 2 个平台地基域）以及可拆分独立微服务（Phase A/B/C）持续演进，跨域通信面临以下核心诉求与技术矛盾：
1. **跨域解耦铁律**：严禁跨域直接 `import` 其他域的 Service 或 Repository（门禁 `npm run microservice:check` 强管控）；
2. **零外部重型依赖交付 (Zero-Ops)**：作为企业级快速启动基座与 NPC 员工开发底座，必须支持单机一键启动与边缘容器部署，不能默认绑架用户部署重型 JVM/Erlang 消息中间件（如 Kafka、RabbitMQ 集群）；
3. **同库同事务可靠投递 (At-Least-Once & Outbox)**：跨域事件必须支持在本地业务事务提交的同时原子落库 Outbox 表，杜绝“业务入库成功但事件丢失”或“事件发出了但业务回滚”的分布式一致性问题；
4. **微服务演进平滑性**：同一套 Domain Facade 抽象，同进程运行时走纯内存 SDK 零序列化直调；拆分部署时走远程协议（自研 NATS 语义或 gRPC），对外契约与消费者代码零修改。

---

## 2. 候选方案拟定 (Candidate Options)

为消灭主观臆断，本决策设立 3 个具有代表性的技术方案（含 1 个阴性对照方案）：

- **方案 A (自研 NATS 语义 + Kysely Outbox 事务表)**：
  在 `@ruoyi/shared` 中内置轻量自研 NATS 请求-响应（Request-Reply）与发布-订阅（Pub/Sub）协议语义，同进程内存派发；跨域独立部署时由 `POST /api/internal/rpc` 或独立 NATS 边缘接入承载；跨域事件通过 Kysely 事务 Outbox 表与 Consumer Inbox 实现可靠重试与幂等消费。
- **方案 B (引入外部独立中间件 RabbitMQ / Apache Kafka 集群)**：
  在微服务拆分后统一要求用户部署外部独立 RabbitMQ 或 Kafka 集群，跨域事件直接推向外部 Broker 队列。
- **方案 C (阴性对照 Baseline: 维持 Node.js 内存 EventEmitter 原生直调)**：
  跨域通知直接调用 Node.js 内置 `events.EventEmitter`，无持久化，无事务边界，进程崩溃消息即丢失。

## 3. 加权评估准则 (Evaluation Criteria & Weights)

依据系统工程评估模型，准则权重总和严格为 100%：

| 准则编号 | 评估维度 | 权重 | 评分标准 (1~5 分) |
|---|---|---|---|
| **C1** | **事务一致性与可靠性 (Outbox / At-Least-Once)** | 25% | 5分: 完美支持同库同事务原子 Outbox 与幂等消费；1分: 无法保障事务，存在单边账 |
| **C2** | **交付与运维轻量化 (Zero-Heavy-Dependency)** | 25% | 5分: 零外部重中间件，单容器/SQLite/Postgres 即跑；1分: 强依赖 JVM/ZooKeeper/重组件 |
| **C3** | **性能与吞吐延迟 (<5ms, 高 RPS)** | 20% | 5分: 内存直通或微秒级通信，单机 RPS $\ge 20,000$；1分: 序列化损耗极大，延迟 >50ms |
| **C4** | **架构演进契合度 (单体/微服务双模对齐)** | 15% | 5分: Domain Facade 底层透明切换，代码 0 改动；1分: 拆分微服务需推倒重构 |
| **C5** | **开源成熟度与许可合规 (License & Stars)** | 15% | 5分: 纯 MIT/Apache-2.0 规范，生态标准；1分: 商业限制或专有协议绑定 |

## 4. 量化评分与敏感度分析 (Quantitative Scoring Matrix)

由技术委员会与架构师小组进行客观量化打分（单项满分 5 分，加权分 = 评分 $\times$ 权重）：

| 方案 | C1 (25%) | C2 (25%) | C3 (20%) | C4 (15%) | C5 (15%) | 综合加权得分 | 排名 |
|---|---|---|---|---|---|---|---|

| **方案 B: 引入外部 Kafka / RabbitMQ 集群** | 4 (1.00) | 1 (0.25) | 4 (0.80) | 3 (0.45) | 5 (0.75) | **3.25** | 第 2 名 |
| **方案 C: 内存 EventEmitter (阴性对照)** | 1 (0.25) | 5 (1.25) | 5 (1.00) | 1 (0.15) | 2 (0.30) | **2.95** | 第 3 名 |

### 敏感度分析 (Sensitivity Analysis)
- 即使将 C5 (开源生态) 权重从 15% 提升至 30%，并将 C2 (轻量化) 权重下调，方案 A 加权总分依然维持在 4.50 以上，显著高于方案 B (3.45)；
- 方案 B 在私有化交付中极大地推高了客户硬件配置要求（至少额外需要 2 核 4G 内存运行 JVM），且在开发调试阶段严重拖慢启动速度，严重违背轻量化设计原则；
- 方案 C 在崩溃与重启场景下 100% 丢失事件，无法支撑资金、库存、支付等核心交易结算，仅可作为不可靠广播使用。

## 5. 决策结论与风险缓解预案 (Decision & Action Items)

### 决策决议
**采纳方案 A** 作为 `ruoyi-all-next` 全域标准消息总线与事务边界方案。

### 潜在风险与缓解行动 (Action Items)
1. **风险 1：Outbox 堆积与磁盘膨胀**
   - *缓解措施*：内置定时清理与归档机制，已投递且超过 7 天的消息自动软删除；配置死信重试上限（默认 5 次），超过上限记录告警日志并转人工审计池。
2. **风险 2：极端并发下的数据库锁争用**
   - *缓解措施*：支持按 `topic/subject` 哈希分片投递，高吞吐场景平滑升级至外部独立 NATS 实例（协议天然兼容）。
3. **架构门禁集成**：
   - 纳入 `npm run microservice:check` 与 `npm run rpc:actions:check`，确保所有事件主题符合 `ruoyi.evt.<domain>.<entity>.<action>` 命名规约。
